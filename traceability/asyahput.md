## Requirement changes

| ID | Original requirement (P4A) | Revised requirement | Why it changed |
|---|---|---|---|
| R2 | The quiz must have exactly the number of questions set by `--count`. Changing only `--count` should not change any other setting sent to the model. | The count the student gives with `--count` reaches the model unchanged, and changing only `--count` changes nothing else the model receives. The quiz view shows and submits exactly as many questions as it was given, with "Question i of N" progress. | **Not feasible as written, and in conflict with other evidence.** The number of questions is written by the model, which we can instruct but cannot force, so "the quiz must have exactly N questions" cannot be guaranteed or checked automatically. It also conflicts with S-4 and O-4, who did not want the quiz to pad a tiny `--diff` with trivial questions just to reach N. What interviewees actually needed (C-2, S-2, O-4) was for the count they typed to be respected and for `--count` not to quietly change anything else. The revised requirement keeps that, covering the parts our code controls: what the model is told, and what the quiz view shows and returns. |
| R4 | Once a question has been answered, esc must ask for confirmation before quitting. Quitting should never send answers for grading, and a re-run should start a completely fresh quiz. | If any question has been answered (a non-blank typed answer, including text still in the answer box, or a picked option), esc must ask for confirmation before quitting. Cancelling returns to the same question with every answer kept; confirming quits without sending anything to be graded. With nothing answered, esc quits right away. A re-run starts a completely fresh quiz. | **Could not be checked as written.** "Once a question has been answered" did not say whether text typed into the box but not yet submitted counts, or what esc does when nothing is answered. A student who types a long answer on Question 1 and presses esc by accident is exactly C-3's worry, so a draft counts as answered. With nothing to lose, an extra prompt would only slow the student down, so esc quits at once. The interview need (S-3: "a 'you'll lose your answers' confirmation would help", "quitting isn't the same as answering") is unchanged. |
| R5 | Each multiple-choice question's correct option must be stored when the question is generated. Grading should compare the student's pick to that stored option, rather than letting the model decide after seeing the pick. | When the quiz asks a multiple-choice question, the label of the correct option is stored with the question before the student answers, and it is never sent to the quiz view. When the answers come back, each pick is graded in code against that stored label, and the model is given the verdict to explain rather than deciding it. If the stored label is missing from the options, the question is reported as ungraded instead of guessed. | **Partly not feasible as written.** The answer key is written by the same model that writes the question, so the code cannot guarantee it was stored at all, or that it matches one of the options. The original wording said nothing about either case, and guessing would bring back the problem O-5 described. Putting the key in the public question schema would also send it to the quiz view, against C-2's "it shouldn't show me the answer before I've answered". The revision keeps what interviewees needed (O-5, S-2, S-4: a verdict fixed before the pick is seen and the same every time). It keeps the key on the tool call only, like the hidden hint, and says what happens when the key is unusable. |

R1 and R3 were kept as written. Both describe deterministic code (the argument parser and the quiz view's navigation state) that we fully control, they do not conflict with any other requirement, and their acceptance criteria are concrete enough to check directly.

## Triage log (Step 3)

Each failure was run against the code as it was before this branch, then classified and fixed.

| Property | Shrunk counterexample | Outcome | What I did |
|---|---|---|---|
| R1 invalid option | First run passed on the original code, even for inputs like `a.ts --diff=yes`, where the error ("Only one file can be quizzed at a time, got 2: a.ts, yes.") does not mention `--diff` | Wrong test | Every error ends with the usage line, and the usage line mentions `--count`, `--level`, `--format`, and `--diff`, so "the message names the option" always passed. The property now checks only the part of the message before the usage line. |
| R1 invalid option (fixed property) | `a.ts --diff=` | Code bug | The parser split `--diff=<value>` into `--diff` plus a value, and the value became a file name. Here an empty string turned into a second file: "Only one file can be quizzed at a time, got 2: a.ts, ." Fixed in `learn-quiz.ts`: only options that take a value are split on `=`, and `--diff=<value>` is rejected with "--diff does not take a value". |
| R1 option given twice | `--format mixed --format mixed` (the same bug lets `--count 50 --count 3` through as a 3-question quiz) | Code bug | The last value silently won, so an invalid `--count 50` was ignored, which is exactly what C-2 and S-2 said must not happen. The example test in `reflection-questions-template.test.ts` asserted the old "grade the answer" wording, so I updated it to the new contract. |
| R4 esc | Quiz `[open, multiple choice]`, nothing submitted yet, draft `"a"` typed in Question 1, then esc: the quiz quit immediately and the draft was lost | Code bug (requirement not implemented) | Added a confirmation step to `quiz.tsx`: esc with anything answered (or a draft in the box) shows "Quit the quiz?
